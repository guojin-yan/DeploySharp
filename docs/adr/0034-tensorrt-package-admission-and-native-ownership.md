# ADR 0034: TensorRT package admission and native ownership / TensorRT 包准入与原生运行时所有权

## Status

Managed inference, ONNX-to-engine building, independent CUDA/RTC execution, opt-in External cache storage, and DeploySharp package publication are admitted. Stage 55 proved the native paths on one pinned local GPU/runtime matrix, and Stages 56-61 retain that proof without manufacturing freshness. On 2026-08-13 the Owner accepted the two missing upstream supply-chain proofs as disclosed residual risk, so they no longer block DeploySharp publication. They remain missing and must not be reported as passed. / managed inference、ONNX 转 engine、独立 CUDA/RTC 执行、显式 External cache 与 DeploySharp 包发布均已准入。Stage 55 已在固定 matrix 上证明 native 路径，Stage 56-61 按 identity 保留该证明而不制造 freshness。两项缺失 proof 仍为披露的 Owner-accepted gap，不得报告为已通过。

## Decision

The exact NuGet.org `JYPPX.TensorRT.CSharp.API 4.0.0` package is admitted as the managed dependency for the isolated adapter. It declares `Apache-2.0`, the formal repository, and tag commit `673e120807d789d90a13a9f28a043282e95bb5e6`; NuGet.org Repository signing verifies successfully. Its 15 TFM folders, 45 managed DLLs, required XML contracts, PE dependency closure, and zero native/model/engine payload pass. The mutable Release still lacks a cross-channel hash manifest and same-build immutable provenance. The Owner accepts that this prevents an independent same-build equivalence claim between the GitHub asset and NuGet.org package, but does not prevent DeploySharp package publication. / 精确 NuGet.org `JYPPX.TensorRT.CSharp.API 4.0.0` 已作为隔离适配器的 managed 依赖准入；许可证、repository commit、签名、TFM/API 与纯 managed payload 均已通过。mutable Release 仍缺跨渠道 hash manifest 与同次构建不可变 provenance；Owner 接受其导致无法独立证明 GitHub asset 与 NuGet.org 包来自同次构建，但该缺口不阻止 DeploySharp 包发布。

The adapter is isolated in `JYPPX.DeploySharp.Backend.TensorRT` and targets `net8.0`. Its inference provider accepts only canonical `tensorrt-engine` `.engine`/`.plan` artifacts. Its explicit builder accepts one validated single-file ONNX artifact, configures workspace, precision policy, optimization level and dynamic min/opt/max shapes, then atomically writes a caller-selected `.engine`/`.plan`. Core and ModelPack remain TensorRT-free. TensorRT, CUDA, cuDNN, NVIDIA drivers, and native bridge files remain consumer-machine owned. Device/runtime/profile-bound plans remain External local-cache data and never enter NuGet, the official catalog, a general model Release, or inventory. Standard TensorRT is not TensorRT-LLM. / 适配器隔离在独立 net8 包中；推理 provider 只接收 canonical engine，显式 builder 接收经校验的单文件 ONNX，配置 workspace、精度策略、优化级别与动态 profile，并原子写入调用方路径。Core/ModelPack 不依赖 TensorRT；native graph 与 plan 缓存继续由 consumer 持有。

## Consequences

Stage 35 covers ten packages and 83 TFM groups; Stage 36 covers ten packages, 83 SourceLink/PDB/API contracts, and 48 managed dependencies. A package-only consumer verifies inference, builder, and CUDA/RTC public contracts without native initialization. The builder returns ONNX/output hashes plus a managed build-input hash, but it does not own a long-lived cache or claim device portability: a complete cache key must additionally bind the exact TensorRT/CUDA/cuDNN/driver/native-bridge/GPU identity. Stage 55 proves execution only for its exact authorized ONNX/kernel/native/GPU matrix; it makes no algorithm-accuracy or performance claim. Publication may proceed under the Owner's risk acceptance, while release documentation must disclose that cross-channel same-build equivalence is unproven. / 纯包 consumer 在不初始化 native 的情况下验证 inference、builder 与 CUDA/RTC 公共合同。builder 返回输入/输出 hash 与 managed build-input hash，但不持有长期 cache，也不声称跨设备可移植；完整 cache key 还必须绑定全部 native/GPU identity。Stage 55 仅证明精确授权 ONNX/kernel/native/GPU matrix 的执行，不声明算法精度或性能。发布可在 Owner 风险接受下继续，但发布文档必须披露跨渠道同次构建等价性未经证明。

## Stage 51 ONNX builder decision / 阶段 51 ONNX builder 决策

The Owner explicitly requested ONNX-to-engine conversion inside the current TensorRT package. `TensorRtOnnxEngineBuilder` is therefore an admitted managed surface. It reads and hashes one regular `.onnx` file, rejects external-data sidecar resolution by using the byte-only parser entry point, validates a caller-owned output path, requires a complete profile for every dynamic non-shape input, and writes serialized host memory through a temporary file followed by an atomic move. FP16 is available only for weakly typed TensorRT 8/10 networks. `Int8ExplicitQuantization` relies on ONNX Q/DQ semantics and intentionally does not enable legacy implicit-INT8 calibration. TensorRT 11 strongly typed precision remains graph-defined. / Owner 明确要求在当前 TensorRT 包中接入 ONNX 转 engine。builder 校验并 hash 单个 ONNX 文件，动态输入要求完整 profile，序列化结果经临时文件原子移动到调用方 External 路径；FP16 仅用于弱类型 TRT8/10，显式 INT8 依赖 ONNX Q/DQ 且不启用旧式校准，TRT11 强类型精度由图决定。

CUDA Driver/Runtime Compilation preprocessing and postprocessing remain a separate future managed execution layer. That layer must use caller-owned streams/device buffers, include compiled-artifact/source/options hashes, and define synchronization and lifetime rules before it is exposed; Stage 51 adds no placeholder CUDA/RTC API or native payload. / CUDA/RTC 前后处理保留为下一层独立 managed execution 能力，必须先固定调用方 stream/device buffer、编译工件/source/options hash、同步与生命周期合同；阶段 51 不加入占位 API 或 native payload。
